El problema

La cocina, la caja y el repartidor trabajan en dispositivos distintos. ¿Cómo ven los mismos pedidos, al mismo tiempo?

Plantea el problema mientras aparece el dibujo: si cada dispositivo guarda su propia copia, las copias se desfasan y alguien trabaja con datos viejos. Pasa igual con un Excel que se manda por correo.

A los dos segundos aparece la solución: una base de datos compartida, una sola fuente de verdad que todos consultan y actualizan.

La arquitectura del curso

Navegador, servidor y Supabase

Cada clase suma un servicio de Supabase. Hoy: la base de datos.

Este dibujo se repite todo el curso. El navegador es lo que ve y usa el usuario: todo lo que llega ahí se puede inspeccionar, así que ahí nada es secreto. El servidor de Next.js consulta los datos, corre la lógica y guarda las llaves; el usuario no tiene acceso a él. Supabase es la base de datos y sus servicios.

  • Filaun pedido

  • idla llave primaria: identifica cada pedido

Una tabla tiene un esquema: cada fila es un pedido y cada columna tiene un tipo (bigint, text, timestamptz) y restricciones (not null, default). La base rechaza lo que no las cumple, venga de donde venga: de la app, del panel o de la API.

El id es la llave primaria: único, lo genera la base (identity) y con él se identifica cada pedido. created_at lo llena la base con now().

Al final aparece un pedido sin descripción: la base lo rechaza. En la práctica creo la tabla en vivo, desde el panel.

Conectar Next.js con Supabase · Idea 3 de 3

La llave publishable es pública

Llave publishable · sb_publishable_

Pública por diseño

Hecha para ir en el navegador: cualquiera la puede ver. Solo puede lo que la base le permita.

Llave secreta · sb_secret_

Acceso total

Se salta RLS. Solo en el servidor; nunca en el navegador ni en el repo. Clase 4.

Lo que protege los datos son las políticas RLS de la base, no esconder la llave. Eso es la clase 2.

Para conectarse, la app necesita dos datos: la URL del proyecto y la llave publishable. Van en .env.local: variables de entorno, configuración que no se escribe en el código ni se sube al repo (el .gitignore ya lo excluye).

Las variables que empiezan con NEXT_PUBLIC_ se incluyen en el código que llega al navegador. Por eso ahí solo va lo que puede ver cualquiera.

Pregúntales: ¿esta llave es secreta? No: es pública por diseño y cualquiera la saca del navegador. Solo tiene los permisos que la base le dé al rol anónimo. La secreta es otra: se salta RLS y solo vive en el servidor. Lo que protege los datos son las políticas RLS, y eso es el viernes. Guarda la pregunta para el cierre.

Leer desde el servidor

Leer: una consulta con select

¿De qué tabla?pedidos.from("pedidos")
¿Qué columnas?todas.select("*")
¿En qué orden?más nuevos primero.order("created_at", { ascending: false })

El resultado: un arreglo

  1. 3Pozole grande para llevaren camino
  2. 2Orden de quesadillaspreparando
  3. 13 tacos al pastor y una horchatarecibido

La consulta corre en el servidor, dentro de la página.
En SQL: select * from pedidos order by created_at desc

Una consulta dice de qué tabla, qué columnas y en qué orden. Con supabase-js se escribe encadenada: from, select y order (del más nuevo al más viejo con ascending: false). Por debajo es una petición HTTP a la API de Supabase, que la convierte en SQL.

El resultado es un arreglo de pedidos, y la página lo renderiza con map, como cualquier arreglo en React.

La consulta va en la página, que es un Server Component: corre en el servidor y el navegador recibe el HTML ya renderizado. Es la idea 1.

Guardar y cambiar corren en el servidor, en una Server Action. Después, revalidatePath le indica a Next.js que vuelva a renderizar la página.

Las cuatro operaciones sobre una tabla, lo que se conoce como CRUD: crear, leer, actualizar y borrar. Hoy usamos tres: select para la lista, insert para el formulario y update para los botones.

Igual que en la idea 1: el formulario no habla con la base; llama a una Server Action, que corre en el servidor y hace el insert.

Después de una Server Action, Next.js no vuelve a renderizar la página por su cuenta. revalidatePath le indica que esa ruta tiene datos nuevos. Si se olvida, el pedido sí se guarda, pero no aparece hasta recargar.

Le indica a Next.js que vuelva a renderizar la ruta.

Después de escribir en la base desde una Server Action, llama a revalidatePath con la ruta que muestra el dato.

Adelántales el error que casi todos se encuentran hoy: la Server Action guarda bien, pero la página no muestra el pedido nuevo hasta que recargan. No es un error de Supabase: Next.js no volvió a renderizar la página.

En la práctica lo provocas a propósito: escribe crearPedido sin revalidatePath y haz un pedido; no aparece. Enséñalo en el panel: sí se guardó. Recarga y aparece. Agrega revalidatePath("/") y el siguiente aparece al momento.

Si preguntan por .env.local: con npm run dev, Next.js lo vuelve a leer cada vez que lo guardan (en la terminal sale Reload env); no hace falta reiniciar.

✕ En SQL, un update sin filtro cambia todas las filas de la tabla.

Un pedido avanza siempre en el mismo orden: recibido, preparando, en camino y entregado. Cada botón lo mueve al estado que sigue.

Para cambiar hacen falta dos cosas: qué cambia (el estado nuevo) y en qué fila. Lo segundo es el filtro: el pedido con ese id, la llave primaria de la idea 2. Cada botón manda en campos ocultos el id del pedido y el estado que sigue.

En SQL, un update sin where cambia todas las filas: es de los errores más caros. Con supabase-js, update siempre va con su filtro, y un filtro equivocado cambia las filas equivocadas.

Problema de seguridad

Hoy tu tabla está expuesta

  • Leer todos los pedidos, con direcciones y teléfonos
  • Crear pedidos falsos
  • Cambiar el estado de cualquier pedido

Nunca así en producción. En la clase 2 lo cerramos con autenticación y políticas RLS.

Haz la demo en vivo antes de esta lámina. En la consola del navegador (F12) pega tres líneas con la URL y la llave publishable:

const url = "https://tu-proyecto.supabase.co/rest/v1/pedidos?select=*";
const llave = "PEGA_AQUI_TU_LLAVE_PUBLISHABLE";
fetch(url, { headers: { apikey: llave } }).then((r) => r.json()).then(console.table);

Salen todos los pedidos, con direcciones y teléfonos, sin pasar por la app. Explícalo tal cual: la tabla no tiene RLS y el rol anónimo tiene permiso de leer, crear y actualizar. La API queda abierta a cualquiera que tenga la URL y la llave publishable, y las dos son públicas por diseño: van en cualquier app que use Supabase desde el navegador.

Lo dejamos así a propósito, para ver el problema. En producción, nunca. La clase 2 lo cierra con autenticación y políticas RLS.
